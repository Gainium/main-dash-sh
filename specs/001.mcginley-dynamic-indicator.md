# 001. McGinley Dynamic indicator — main-dash-sh slice

Feature spec — new behaviour, no existing behaviour is being changed.
Cross-repo companion to `indicators`' `specs/002.mcginley-dynamic-indicator.md`
(the math + `IndicatorEnum.mg` + config `{ type; interval }`) and `app-sh`'s
`specs/006.mcginley-dynamic-indicator.md` (the bot-engine/API wiring — no
bespoke `SettingsIndicators` fields, reuses `indicatorLength`/
`indicatorValue`/`indicatorCondition`).

This repo is the dashboard's core (`main-dash-redesign`'s `core/`
submodule). **All indicator code for the current dashboard lives here** —
the outer repo has none of its own.

## §1 Behaviour

- A user can select **McGinley Dynamic** from the bot-settings indicator
  picker, the same as any other indicator, with its condition/threshold
  fields (length, interval, condition, value) rendering **automatically**
  from a declarative catalog entry — no hand-written JSX, per this repo's
  catalog-driven architecture (`INDICATOR_CATALOG`).
- Adding it to a chart draws a **TradingView custom study**: a single line
  overlaid on price (like `EMA`/`WMA`), following §2's formula. This is a
  from-scratch reimplementation in TradingView's own primitives
  (`customIndicators.js` does not import `@gainium/indicators`) — the
  math must be kept in sync by hand between the two repos.
- Backtesting a bot using McGinley Dynamic from this dashboard depends on
  `@gainium/backtester` having a matching `mg` entry — already a named,
  out-of-scope gap in the `indicators` repo's plan (a separate backtester
  PR). Not fixed here; the catalog/chart-study work is independently
  useful (a user can see the indicator, add it to a bot) even before that
  gap closes.

## §2 Formula (chart study)

Same source as the `indicators` repo's spec — the requester's Pine Script:

```
mg[0] = close[0]
mg[n] = mg[n-1] + (close[n] - mg[n-1]) / (length * (close[n]/mg[n-1])^4)
```

No `r.Std.*` builtin computes this (TradingView's own `r.Std.ema`/`sma`/
etc. don't include McGinley Dynamic), so — like `LW` (Long Wick, the most
recent precedent, which also hand-computes stateful levels with no
builtin) — the chart study computes it by hand using
`this._context.new_var(NaN)` to persist the previous bar's value and
`.get(1)`/`.set(...)` to read/write it. This is a **fully portable** Pine
Script (Step 0's classification): pure math, plots a single value/line, no
drawing objects (`label.new`/`box.new`/etc.) — the chart study can be a
faithful port, not an approximation.

## §3 Open questions

- **Which existing indicator is the closer template: `LW` or the `ma`
  family (`EMA`/`WMA`/...)?** Investigated both. `ma`'s family is richer
  (source/offset/smoothing options, `maCrossingValue`/`maType` for a
  *reference-comparison* mode) because `app-sh`'s `ma` case is itself
  richer than what this integration needs. `LW`'s shape (single input set,
  hand-computed via `_context.new_var`, no builtin) matches McGinley's
  *shape* (no `r.Std` equivalent), but `LW`'s specific fields (bull/bear
  levels, dual plots) don't apply. Resolved: **structure the study like
  `LW`** (hand-computed state, single input `length` + hidden `id`, per
  the minimal `ATR` template for input/plot wiring, since `ATR` is the
  simplest single-plot precedent with a plain callback
  `callback(value, id)` — not `LW`'s `callback({id, ...fields})`, which
  is for multi-field results only) — see plan for the concrete file.
- **Catalog `fields` array — must exactly match what `app-sh` actually
  reads.** `app-sh`'s spec §2 decision was: McGinley reuses *only*
  `indicatorLength`/`indicatorInterval`/`indicatorCondition`/
  `indicatorValue` — no bespoke fields (unlike `ma`'s
  `maCrossingValue`/`maType`/etc., which `app-sh` has dedicated handling
  for and McGinley does not). The catalog entry here must mirror `ATR`'s
  field list exactly, **not** `ma`'s — using `ma`'s richer fields would
  silently produce settings `app-sh` never reads.
- **`STUDY_NAME_MAP` value must equal the study's own `name`/
  `description` string.** Confirmed by reading `ATR`'s pair (`'Average
  True Range (Custom)'` in both places) and `LW`'s pair (`'Long Wick
  Detector'` in both, no `(Custom)` suffix since it isn't a TradingView
  builtin reimplementation). McGinley Dynamic isn't a TradingView builtin
  either, so it follows `LW`'s naming style — no `(Custom)` suffix.

## §4 Non-goals

- No change to `src/mappers/bots/dca/field-mapping.ts` or
  `formDefaults.ts` — grepped for per-indicator-type branches there; the
  only one (`IndicatorEnum.lw`) exists solely to coerce `LW`'s bespoke
  string fields. McGinley has none, so nothing to coerce (matches `ATR`/
  `ADR`, which also have no entry there).
- No `BOT_CONTROLLER_EXCLUSIONS` entry — that list is for filters
  (Session-style) that shouldn't appear in the bot-controller UI; McGinley
  is a normal candle-driven indicator.
- No `content` repo help page — out of scope per the user's 3-repo
  instruction (same gap already flagged for the `indicators`/`app-sh`
  legs). The catalog's `INDICATOR_DOCUMENTATION_URLS` entry will point at
  a URL slug (`/help/mcginley-dynamic`) that doesn't resolve yet — named,
  not silently shipped as if it worked.
- No `main-dash-redesign` (outer repo) change — this repo *is* its
  `core/` submodule; the outer repo's only involvement is a pointer bump
  + version + CHANGELOG, out of scope for this repo's own PR.
